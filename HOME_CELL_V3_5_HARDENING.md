# Home Cell v3.5 — security and reliability

## Install this update

1. Keep your existing `.env.local`. Extract this complete project to a new folder; do not mix old `node_modules` or `.next` output into it.
2. Apply any missing Home Cell migrations in order through 014. Apply **supabase/015_home_cell_rate_limits.sql** in the same Supabase project's SQL editor before starting this version. 015 is additive and rerunnable; it does not delete existing members, leaders, assignments, reports or visitors.
3. Set the server-only `SUPABASE_SERVICE_ROLE_KEY` in local and hosting environments. Never use `NEXT_PUBLIC_` for it. An optional separate `HCO_RATE_LIMIT_SECRET` can hold a random secret of at least 32 bytes; otherwise the service key hashes the counters. Do not send keys to another person or paste them into the source.
4. Run `npm ci`, `npm run typecheck`, `npm run test:reliability`, `npm run test:home-cell`, and `npm run build`. Start locally with `npm run dev`; production uses `npm start` or the existing Netlify adapter.
5. Test real email and phone username login, personal password activation, existing member assignment, CSV import and a coordinator/admin transfer decision with dedicated test accounts. The included browser checks use a local Supabase fixture; they cannot prove live project settings or provider delivery.

If 015 is missing or its RPC is inaccessible, Home Cell login and recovery return 503 rather than silently disabling brute-force protection. Verify migrations, the project URL and server key. Never run old reset/drop scripts to repair this. Member Care's original login still uses Supabase's own auth protections.

## Implemented in v3.5

- Next.js pinned to **16.4.1**, lockfile updated; installed image processor **sharp 0.35.5**. Addresses the October 14 framework advisory. Do not roll back to vulnerable 16.4.0 during an incident. Official reference: https://nextjs.org/blog/nextjs-security-update-october-14-2026.
- Shared, atomic PostgreSQL login/recovery counters work across app instances. Limits per five-minute fixed window: login 60/IP and 10/normalized identifier; recovery 15/IP and 3/email. Attempts count even if they fail. Phone formatting is normalized before account throttling. These endpoint-specific counters contain keyed hashes, not raw emails, phones or IPs. Fixed windows permit bursts across a boundary; this is not a complete DDoS defense.
- The application trusts the Netlify connection-IP header only when `NETLIFY=true`, validates its format, and ignores caller-supplied `X-Forwarded-For`. Local development and other hosts share an unknown-IP bucket. Before using another host, implement and verify its trusted proxy policy. A proxy in front of Netlify may aggregate users behind one IP. Identifier limits still apply. Changing hashing secrets resets bucket identity.
- Expired rate counters are removed in bounded batches during requests, after a one-hour grace period. Low traffic can leave expired rows longer; no scheduled retention guarantee is claimed. Indexed expiration supports cleanup.
- Supabase clients use an eight-second timeout signal per outbound attempt (including response body consumption). GET/HEAD calls have at most one application retry with short jitter for network errors or 502/503/504. POST/PATCH/DELETE and RPC writes have no application replay. A timeout can occur after the server committed a write: reconcile or retry the same existing idempotency key. Do not generate a new batch key to retry uncertain onboarding. Supabase's own SDK/auth retry behavior is separate. Application throttling complements Supabase Auth limits; it cannot replace protections on the public Supabase Auth service itself.
- Home Cell JSON mutations have a streaming 300 KiB envelope limit; login/recovery use 4 KiB. Malformed JSON and unsupported media types return clear errors. Existing CSV validation still applies: at most 100 rows and 200 KB CSV content, within the envelope limit. Oversized requests are rejected before business mutations.
- All Home Cell API responses include private/no-store cache headers and a generated `X-Request-ID`. Structured request logs contain fixed route label, method, status, duration and request ID. They omit query strings, member details, request bodies, passwords, tokens and raw error objects. Existing deliberate permission errors retain their responses; uncaught errors return a generic 503.
- Browser security headers deny framing and object embedding, restrict the base URL, disable MIME sniffing, restrict referrers and disable unused device permissions. The CSP is deliberately limited; it is not a complete script/XSS policy. Existing React escaping, field validation and parameterized database access remain essential.
- A GitHub Actions workflow runs type checks, domain/database tests, production build, Gateway HTTP integration, fixture-backed browser checks and production dependency audit. It becomes active only if this project is committed to GitHub with Actions enabled. It does not deploy or apply SQL. The lockfile and `npm ci` provide repeatable dependencies.

The existing public Gateway also accepts its optional email field when blank, disabling only that unavailable email channel. Existing email/SMS defaults and other category preferences remain unchanged; outbound sending stays independently gated.

## How the supplied engineering topics apply

| Topics | Treatment in this application |
| --- | --- |
| Rate limiting, timeouts, retries, exponential backoff, idempotency | Shared auth counters and bounded outbound calls added above. Existing onboarding, guest gateway and report RPCs use explicit idempotency or uniqueness guards. No write retry is inferred safe from HTTP success/failure alone. |
| Caching, reverse proxies, load balancing, API gateway, serverless/cold starts | Netlify/Supabase deployment architecture; static assets can use CDN caching. Authenticated member data stays private/no-store. Keep warm-path work bounded and measure before adding another gateway or process cache. No local session cache bypasses role revocation. |
| Indexes, query optimization, N+1, pooling, throughput, p99/tail latency | Existing cell/date, membership and role indexes remain. New counter expiry index added. Supabase Data API manages database connections; no per-request direct PostgreSQL pool added. Existing bounded directory lookups are a future measurement target, not falsely described as removed. Use EXPLAIN in staging with representative data before adding indexes, read replicas or partitions. |
| Transactions, races, optimistic/pessimistic locking, deadlocks | Existing SQL transactions, row locks, version checks, unique constraints, scope validation and batch locks remain covered by database regressions. Transfer requests retain original membership until an authorized decision. On serialization/deadlock errors, reconcile and retry with the same request key. |
| Queues, pub/sub, events, DLQs, sagas, cron | There is no new external messaging worker. Existing communications UI/job records do not mean real email/SMS delivery is running. Add a durable queue, unique delivery key, bounded worker retries and DLQ only when actual asynchronous delivery is commissioned. No distributed transaction is needed for the current single-database member/transfer operations. |
| SSE, websockets, polling | Existing explicit refresh and normal API requests fit current workflows. No unneeded persistent connections added. Add realtime transport only for a concrete live-update requirement with scoped subscription authorization. |
| Circuit breakers, service discovery, leader election, distributed locks | Current app uses configured Supabase endpoints and database transactions. No cluster coordination layer is justified. Provider outages fail closed; adding a per-process breaker would not coordinate serverless instances. Consider one only after measuring outage amplification. |
| Docker, Kubernetes, Helm, Terraform, IaC, multiregion | Existing `netlify.toml` remains the deploy configuration. New clusters, replicas, Terraform state and regions were not provisioned. Add infrastructure only with a defined requirement, budget, credentials and operational owner. |
| Replication, CAP, consistency, sharding, partitioning, network partitions, clock skew | Core writes use the primary database and DB time. No eventually consistent cache decides permissions or membership conflicts. Sharding/read replicas can invalidate these assumptions and require a separate design. |
| Observability, metrics, tracing, alerts, SLI/SLO/error budgets | Request IDs, sanitized structured logs and duration/status fields added. Aggregation, dashboards, alerts and end-to-end distributed traces require provider/monitoring setup; they are not silently active. Suggested starting targets and incident procedure below. |
| Secrets, IAM, OAuth, JWT/key rotation, TLS, encryption, WAF/DDoS | Service key remains server-only, least-privilege/RLS and scoped RPCs remain. Supabase handles auth tokens. Hosting account MFA, secret rotation, HTTPS, backup encryption and edge abuse policies must be verified by the operator. Do not add OAuth if email/password login meets the current requirement. |
| CORS, CSRF, SQL injection, XSS, SSRF | Existing same-origin mutation checks, HTTP-only same-site cookies, validated inputs and database parameters remain. No wildcard CORS added. New CSP is defense in depth. Server calls use configured Supabase endpoints; no arbitrary user-provided URL fetch feature was added. |
| Migrations, schema/API/semantic versioning, backwards compatibility | Numbered additive SQL 015; previous rows remain. Existing public gateway contract stays unchanged. Versioned ZIP and lockfile identify the release. No incompatible `/api/v2` endpoint created without a contract change. |
| Disaster recovery, backups, failover, chaos testing | Restore drill/runbook below. No live backup, failover or chaos test was performed. Provider plans determine available recovery options. Fault tests simulate upstream failures locally. |
| Cost, build caching, dependency updates | CI caches npm downloads, uses bounded execution and cancels superseded runs. Lockfile controls versions. Review billing and dependency alerts regularly. Cost budgets/alerts require provider setup. |
| DNS, TCP/UDP, HTTP/2/3, gRPC, webhooks | Existing HTTPS JSON endpoints and authenticated/idempotent WordPress webhook fit these integrations. Transport negotiation and DNS are hosting concerns. gRPC and custom transport servers would add complexity without a current use case. |
| Incidents, on-call, postmortems, memory leaks | See operational procedure. No long-lived in-memory member/credential cache added. Body readers release locks; retry abort listeners are removed; timeout signals are bounded. Long-run memory profiling and real load tests still need a staging environment. |

## Operator setup and recovery

Before production, identify an administrator and backup owner. Check Supabase backup availability/retention for the actual plan; configure a suitable encrypted backup location and limited restore permissions. Verify Netlify HTTPS/custom domain/DNS and the correct production Supabase redirect allowlist. Enable MFA for provider administrators. Set secrets in environment settings, never GitHub source, logs or public variables. Run live smoke checks against a preview/staging project before promoting the release.

Suggested initial service objectives (targets, not measured guarantees): 99.5% successful protected API requests monthly excluding expected user validation/permission errors; p95 API latency below 2 seconds; alert on repeated 5xx/503 or sustained abnormal login 429 volume, not an isolated invalid password. Track p99 separately so averages do not hide slow requests. Aggregate logs externally with access controls and an explicit retention policy. Export only sanitized events. A 503 from rate protection means check the 015 RPC/service configuration and database health; do not bypass it to restore access.

Recovery target to agree before launch: RPO 24 hours and RTO 4 hours as a starting point. If that data-loss window is unacceptable, enable a provider-supported PITR plan and set tighter targets. Run a restore drill into an isolated project: restore schema/data, confirm auth identities and private username mappings, apply missing forward migrations, test role scopes and one complete transfer, and record measured RPO/RTO. Auth backups and storage objects may require separate procedures; confirm what the provider backup actually includes. Never overwrite the live project during a drill. Do not export member data into this source ZIP.

For an incident: note UTC start time, release/version and sanitized request IDs; inspect provider status and error rate; restrict the affected integration if necessary; preserve audit history; restore service with a known secure build compatible with the current additive schema. Do not reverse migrations with destructive drops. If a write timed out, inspect its stored request key/result before retrying. If a secret leaked, rotate it through the provider and update the server environment; verify existing sessions/recovery behavior and access revocation. Finish with a short incident record: impact, timeline, root cause, fix and one accountable prevention action.

No provider settings, hosted SQL, real credentials, backup schedules, alert destinations or production deployments were changed by this package.
